# Measurement contract

The workload is a paced request/echo exchange, with one logical request outstanding per client. It measures application goodput and RTT under this workload, **not maximum link capacity or unidirectional bulk-stream throughput**. A fresh server and fresh connections are used for each trial. Connection establishment is excluded from the client measurement window. Client workers synchronize after connect; the window includes their initial payload setup, pacing, validation, and final join. CPU uses `getrusage(RUSAGE_SELF)` user + system time across all threads. CPU percent is CPU seconds / wall seconds × 100, so a process using multiple cores can exceed 100%.

## Units and denominators

- Payload: application data, excluding the 24-byte protocol header, TCP/IP, UDP/IP, Ethernet, and echoes.
- Goodput: complete, byte-validated logical payloads × 8 / measured wall seconds / 1,000,000, in decimal Mbps. Divide by 1,000 for Gbps. Request payload is counted once; the echo produces additional traffic.
- RTT: elapsed `CLOCK_MONOTONIC_RAW` time from before request buffer preparation to after receiving and validating its complete echo. Includes application work, scheduling, and socket work. No one-way latency is reported.
- Quantiles: nearest rank on the pooled successful RTT samples across workers, without interpolation. Timeouts are counted separately, not inserted as successful latency samples. This creates survivor bias when loss occurs; read latency alongside completion and timeout counts. Very small samples do not establish reliable tail latency. A run with no completed messages has status `no_samples`, null latency, and a nonzero client exit.
- UDP missing echoes: sent datagrams minus unique, validated echoes received before the logical-message deadline. This is **application-level round-trip echo loss**: either request loss, response loss, or excessive delay can cause it. It cannot isolate the forward path, kernel drops, or network drops. No TCP packet-loss metric is derived from `recv()`.
- UDP missing messages: attempted logical messages minus complete logical echoes. A large message is unsuccessful if even one of its fragments is missing. A timeout aborts the remaining fragments; unsent fragments do not enter the datagram denominator. Late echoes are counted as stale when read during a later logical message and do not retroactively repair an expired result.
- Effective buffers: `getsockopt(SO_SNDBUF/SO_RCVBUF)` on every client and the server listener/socket. Linux may clamp and double requested buffer sizes. A TCP receive buffer can also change through autotuning; these are connection-setup observations, not continuous samples.
- Server CPU: runner records CPU seconds for the server benchmark lifetime after CLI parsing, including socket setup, idle time, and shutdown. It is not an exactly synchronized server active-window CPU percentage. Client active-window CPU percent is the plotted CPU measure.

## Bounds and pacing

Default: loopback, 1 client, 1 second, up to 1,000 messages/client, aggregate request payload cap 100 Mbps and aggregate request rate 10,000 logical messages/second. The first duration/message limit stops new messages. A started message can finish or time out after the configured duration. No attempt is made to interrupt a frame midstream solely to hit the duration limit.

The CLI caps concurrency at 32, duration at 60 seconds, payload at 1 MiB, aggregate configured rate at 100,000 requests/second and 1,000 Mbps, and messages × clients at 1,000,000 per iteration. Iterations are finite (maximum 100). These are application request caps, not strict wire-rate shapers. TCP can initially burst one bounded message per client. Echoes and protocol overhead are extra. The benchmark is not an unbounded sender. Since the first message starts immediately, finite-window goodput can exceed the nominal scheduling cap by up to one payload per client per measured window. In particular, 1 MiB TCP messages in a 0.6 s window can yield approximately 111.8 Mbps at a nominal 100 Mbps setting. This is a discrete-message boundary effect, not evidence of exceeding a link limit.

UDP fragments are at most 1,200 payload bytes plus 24 header bytes. Each fragment is echoed before sending the next; no retransmissions are performed. Fragment pacing apportions the per-message interval across fragments, so large UDP message RTT **includes deliberate pacing**. A 1 MiB UDP logical RTT is not comparable to the RTT of one native UDP datagram. This implementation avoids IP fragmentation on common Ethernet MTUs, but 1,224-byte datagrams are not guaranteed to fit every network path. TCP uses one logical frame per request.

Pacing uses relative `nanosleep()` calls checked against RAW-clock targets and does not busy-spin. The next target is advanced from the actual start when behind schedule to avoid accumulating catch-up bursts. Sleep/scheduler overhead can prevent reaching the cap. Large UDP messages or very low caps may need a larger `--timeout-ms`; that deadline includes intentional fragment pacing. Blocking syscalls use short kernel timeouts (50 ms) for shutdown responsiveness. Deadlines are checked between syscalls; blocking calls can overshoot a deadline by up to one kernel timeout plus scheduling delay. Nonblocking I/O waits with `poll()` in chunks of at most 50 ms. No hard real-time guarantee is made.

## Experimental controls

The runner records the compiler, CMake cache/build type, kernel, CPU model, affinity, memory, load average, CPU governor, socket sysctls, exact commands, timestamps, binary SHA-256, and a source archive. There is no dependency on repository commit history to reconstruct the snapshot. It randomizes trial order with a recorded seed and keeps raw stdout/stderr, return codes, failed/incomplete records, and separate warmup records. Warmup runs warm the process/code environment but do not remove first-message effects from each new connection.

Use release builds for measurements. Sanitizer builds are correctness tools, not comparable performance measurements. Prefer an otherwise idle machine and several seconds per trial, at least 5–10 repetitions, and enough messages for tail percentiles. The included short runs are bounded local characterization; they do not substitute for longer runs on representative hardware. Sample spread and per-trial variation are more informative than one best number. Randomized order reduces drift bias but does not eliminate scheduler, frequency, thermal, or background-work effects. No CPU isolation, fixed frequency, hardware timestamping, or clock synchronization is claimed.

The plots show mean trial summaries and min/max ranges across repeated trials, not confidence intervals. Pooled message quantiles within one trial differ from quantiles across trial means. Comparisons must hold transport, payload, clients, buffers, pacing, duration, mode, and TCP_NODELAY constant except for the factor under investigation.

## Historical timing correction

The initial `results/baseline/` snapshot could stop before the last unsent pacing target reached the duration boundary. Its 1 MiB TCP trials reported about 119 Mbps over roughly 0.422 s instead of waiting to 0.5 s. Those records are preserved unchanged and are excluded from the primary optimized/baseline plots. The controlled `comparison` and `survey` snapshots wait to the configured end when the next scheduled start lies outside the window. Finite-message overshoot described above remains explicit. Their baseline/optimized comparisons use identical timing code.

Analysis rejects pooled comparisons when fixed workload controls differ across campaigns. Missing successful variants remain missing rather than becoming zero-height bars. Plot captions use recorded settings, and failed-trial totals remain visible in the aggregate tables.
